# Implementation Plan: Admin module portal

Intent confirmed 2026-10-13 (interview). Local only, like the other dev-only plans in `tasks/`. `tasks/plan.md` and `tasks/todo.md` are complete SDK-gate plans and are not touched; `tasks/admin/` holds the admin-area plan, which this builds on. This plan and its task list live in `tasks/admin-portal/`.

## Overview

Make `/admin` a portal where a new admin feature is one folder: `app/admin/_modules/<id>/`. The folder holds a manifest (label, required permission, order), a page, and optionally its own server actions, components and tests. The portal builds nav, the `/admin` redirect and the access check from the manifests. Adding a module edits no file outside its folder.

## Out of scope

- Migrating the five existing admin pages (config, roles, quarantine, errors, reports). They keep working and stay in `ADMIN_PAGES`; the nav merges both sources.
- DB migrations and cron: stay central (Supabase and Vercel config need ordering).
- Player-facing UI. Runtime or third-party plugin loading.
- A shipped sample module in production (see decision 5).

## What already exists (reuse)

- `lib/services/authorize.ts` `authorize(permission)` and `lib/services/rbac.ts` `can`, `Permission`. Reads role from the DB per request.
- `app/admin/layout.tsx` (floor gate at `disputes.resolve`, nav), `components/admin/AdminNav.tsx`, `AdminDenied.tsx`, `lib/constants/admin-pages.ts`, `app/admin/page.tsx` (redirect to first allowed page).
- `tests/admin-shell.test.tsx`: the `signInAs(role)` helper and layout assertions. Extend it, do not duplicate.
- `.dependency-cruiser.cjs`: `lib` must not import `app` or `components`. Coverage `include` and Semgrep scan `app/`, so modules under `app/` are measured with no config change.

## Architecture decisions

1. **Location `app/admin/_modules/<id>/`.** Underscore folders are private to the Next router (no route), and `app/` is already inside coverage, depcruise, Semgrep and tsc scopes. A top-level `modules/` dir would need all four scopes widened. `lib/` is out: modules hold UI and `lib` may not import `app` or `components`.
2. **Auto-discovery by codegen.** Next with Turbopack has no `require.context` or `import.meta.glob`, and a runtime `fs` scan is not traced into Vercel serverless output. `scripts/gen-admin-modules.mjs` scans the folders and writes `app/admin/_modules/registry.generated.ts` with static imports (manifests) and a lazy `() => import('./<id>/page')` loader per module. The file is committed so a fresh clone type-checks. It is regenerated by `predev`, `prebuild` and `pretest`; a test fails if the committed file is stale, so CI catches a forgotten run.
3. **Contract.** `manifest.ts` default-exports `{ label, permission: Permission, order? }`, typed `AdminModuleManifest`. The `id` is the folder name (kebab-case, so it is the URL segment). `page.tsx` default-exports a server component receiving `{ role, segments }`. Manifests must be pure (no server imports): the nav imports them.
4. **One catch-all route, central authorization.** `app/admin/[...module]/page.tsx` takes the first segment as the id, `notFound()` if unknown, then `authorize(manifest.permission)` before it loads or renders the module. A module author cannot forget the check on the page. Writes are still the author's job: server actions call a service that authorizes, per the rule in `lib/actions/admin-actions.ts`. Static routes (`/admin/config`, ...) win over the catch-all, so existing pages are unaffected.
5. **No sample module ships to production.** It would appear in every admin's nav. Instead: `app/admin/_modules/_template/` (skipped by the generator because of the underscore, still type-checked and linted) is the copy-paste starting point, and tests run the generator against a fixture module dir. The generator takes the root dir as an argument for this.
6. **Generator guards.** It fails the build on: id not kebab-case, id equal to a static `app/admin/*` folder (collision with an existing page), missing `manifest.ts` or `page.tsx`, duplicate ids. Permission validity is checked by `tsc` through the manifest type, not re-implemented in the script.
7. **Nav and redirect read one merged list.** `lib/constants/admin-pages.ts` stays for the five legacy pages (it is in `lib`, so it cannot import module manifests). A new `app/admin/_modules/nav.ts` `adminNavItems(role)` merges `ADMIN_PAGES` and module manifests, filtered by `can`, sorted by `order` then label. `AdminNav` and `app/admin/page.tsx` call it.
8. **Branch.** Base branch is an open question (below). Default: worktree `feat/admin-modules` off `preview`, as `feat/admin-area` was, merged into `company/update-code` when done. No PR until the owner says.

## Risks and mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Generated file forgotten or stale | Module missing from nav | Drift test in CI; `predev` and `prebuild` regenerate |
| Lazy `import()` per module pulls module code into every admin page | Bundle growth | Loader is only called inside the catch-all route; public routes never import the registry. `check:bundle` in T2 verification |
| Module id shadows an existing admin route | Silent dead module | Generator fails on collision with `app/admin/*` folders |
| Author skips authorization on a module server action | Privilege escalation | Docs and template show the service-authorizes pattern; page-level check is central |
| Nav shows a link the role cannot open | Confusing, not a leak | Nav filters by `can`; the route checks again |
| `scripts/` generator not covered by coverage `include` | Untested logic | Logic lives in a small exported function; tested directly with a fixture dir |
