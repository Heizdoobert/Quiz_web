## SECURITY-TRADE-OFFS.md claim check

False or inaccurate:
- 4.A "state-changing Server Actions (`createQuestion`, `submitAnswer`, ...) authenticate the caller through the signed cookie": `submitAnswer` does not require a session; guests receive the correct answer (quiz-actions.ts:73-93). See S2-02.
- 4.B "public key cannot write" / "All writes go through `supabaseAdmin`": migrations leave `user_ai_usage` without RLS and `increment_ai_generation` executable by anon (18-ai-usage.sql). Unverified against the live DB. See S2-05.
- 1 Spoofing, "replaying a SIWE signature ... nonce ... deleted on first use": the nonce is checked only against a caller-controlled cookie, and the domain is taken from the Host header, so replay and relay protection is overstated (auth-actions.ts:71-86). See S2-11.
- 1 "Writes require a session account": `syncContestStatus` writes list status with no session (question-list-actions.ts:552-587). See S2-20.
- CONSTRAINTS.md says Semgrep, a11y, perf and changed-line coverage run in CI or at preview deploy; ci.yml and cd.yml have none of them. See S2-15.

Partly true:
- 1 "Raw database errors ... replaced with generic messages": true for DB errors; `signUpWithUsername` returns Supabase Auth `error.message` (auth-actions.ts:186).
- 2 "Per-IP limits use the first `x-forwarded-for` hop set by the hosting proxy": literally true (rate-limit.ts:43-44), but only holds on a hosting platform that overwrites the header; self-hosted docker-compose does not. See S2-09.

Confirmed true (checked against code):
- Rate-limit table (auth-actions.ts:69,105-106,118,150-151,217,262), hashing, blocked attempts not recorded, fail-open behavior and `auth_rate_limited` log (rate-limit.ts:22-36; 17-auth-rate-limit.sql:28-38).
- `requestEmailCode` returns `{sent:true}` for any address and applies the same limits (auth-actions.ts:100-113); username enumeration and the 15-minute lockout are disclosed accurately.
- Headers: `X-Content-Type-Options`, `X-Frame-Options`, enforcing `frame-ancestors`, report-only CSP, HSTS, Referrer-Policy and Permissions-Policy (next.config.mjs:76-85; tests/security-headers.test.ts exists).
- Session cookie flags (session.ts:53-59); `getUserQuizzes` selects display fields only (profile-actions.ts:50); `exportUserData` is session-bound and capped (profile-actions.ts:96-125).
- 4.C: `buildTokenClaimVoucher` no longer exists in lib/ or app/ (grep: no matches); `startContest` checks the on-chain pool and creator (question-list-actions.ts:520-524); `claimListReward` refuses when the pool cannot be read (903-908); one open voucher per account via `reward_claims_one_open_contest_per_account` (accounts.sql:168).
- 3: `next` is 16.4.0 (package.json:37); baseline `npm audit --omit=dev` shows 0 vulnerabilities; CI runs `npm run check:deps` with `--audit-level=high` (ci.yml:178-181, package.json:20).

## Positive observations
- Every state-changing action except the ones above derives identity from the signed cookie and keys writes on `account.id`; ownership checks are present on lists (`getOwnedDraftList`), comments (`deleteComment`, `resolveSuggestion`), contest start and refund.
- Server actions get Next's built-in Origin check and the cookie is `sameSite=lax`, so no CSRF path was found. The only route handler that changes state does not use cookies (csp-report).
- Uniform `{ sent: true }` response and hashed rate-limit keys; `rate_limit_hit`, `sweep_to_treasury`, `get_treasury_entitled_count` are correctly revoked from PUBLIC/anon.
- `correct_index` and `explanation` are excluded from anon column grants (schema.sql:77-80); `users.auth_user_id` is not readable by anon (accounts.sql:224-225).
- No SSRF or open redirect: the server fetches only fixed RPC and Gemini endpoints, and there are no `redirect()` calls on user input. UUID validation and ILIKE escaping are applied before PostgREST filters.
- Secrets: only `NEXT_PUBLIC_*` values that are public by design reach client code; gitleaks and semgrep are clean in the baseline; `.env` is gitignored.
